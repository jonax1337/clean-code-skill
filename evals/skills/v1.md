# CLEAN CODE (Robert C. Martin)

> „Clean code can be read, and enhanced by a developer other than its original author.“

Quelle: *Clean Code – A Handbook of Agile Software Craftsmanship* (Kap. 2–13 und Kap. 17 „Smells and Heuristics“). Der vollständige Heuristik-Katalog C1–T9 steht in [`references/heuristiken.md`](references/heuristiken.md). Bei Reviews die Codes zitieren (z. B. „verletzt G5, F3“).

## 0. Priorität: Becks 4 Regeln des einfachen Designs (Kap. 12)

Bei jedem Konflikt gilt diese Reihenfolge:

1. **Alle Tests laufen.** Nicht testbarer Code ist nicht fertig.
2. **Keine Duplikation** (DRY, G5). Jede Wiederholung ist eine verpasste Abstraktion.
3. **Drückt die Absicht aus.** Gute Namen, kleine Funktionen, Standardbegriffe.
4. **Minimale Anzahl von Klassen und Methoden.** Alles, was nach 1–3 übrig ist und keinem Zweck dient, kommt weg.

**Weniger Code** heißt also: kein Element ohne Zweck, keine Duplikation, kein toter Code (F4, G9), kein Durcheinander (G12), keine Überkonfiguration. Es heißt **nicht**, Lesbarkeit zu opfern. Eine extrahierte Funktion mit gutem Namen ist erlaubt, auch wenn sie Zeilen kostet (Regel 3 vor Regel 4).

## 1. Namen (Kap. 2)

- Absicht offenlegen: Der Name beantwortet, warum es existiert, was es tut und wie es benutzt wird. Braucht ein Name einen Kommentar, ist er falsch (N1).
- Keine Desinformation (`accountList`, wenn es keine Liste ist) und keine Rausch-Unterscheidungen (`a1/a2`, `ProductInfo` vs. `ProductData`).
- Aussprechbar und suchbar. Keine magischen Zahlen, sondern benannte Konstanten (G25). Länge proportional zum Scope (N5).
- Keine Codierungen: keine ungarische Notation, kein `m_`, kein `I`-Präfix für Interfaces (N6).
- Klassen sind Substantive (`Customer`, `AddressParser`), Methoden sind Verben (`save`, `deletePage`). Keine `Manager`/`Processor`/`Data`/`Info`-Füllwörter.
- **Ein Wort pro Konzept** (`fetch`/`get`/`retrieve` nicht mischen). Kein Wortspiel: ein Wort nicht für zwei Bedeutungen.
- Namen aus der Lösungsdomäne (Patterns, Algorithmen) oder aus der Problemdomäne, abstraktionsgerecht (N2, N3). Eindeutig (N4). Seiteneffekte gehören in den Namen (N7: `createOrReturnOos`, nicht `getOos`).

## 2. Funktionen (Kap. 3)

- **Klein. Und dann noch kleiner.** Selten über 20 Zeilen. Blöcke in `if`/`else`/`while` sind idealerweise eine Zeile, nämlich ein Funktionsaufruf. Höchstens 1–2 Einrückungsebenen.
- **Eine Sache tun** (G30). Test: Lässt sich eine weitere Funktion mit einem Namen extrahieren, der nicht nur die Implementierung nacherzählt, dann tut sie mehr als eine Sache.
- **Eine Abstraktionsebene pro Funktion** (G6, G34). Die **Stepdown-Regel**: Code liest sich von oben nach unten wie eine Erzählung, jede Funktion steigt eine Ebene tiefer.
- `switch` nur einmal, versteckt hinter Polymorphismus oder einer Abstract Factory (G23).
- **Argumente:** 0 ideal, 1 gut, 2 akzeptabel, 3 vermeiden, mehr als 3 nur mit sehr guter Begründung. Sonst zu einem Argumentobjekt zusammenfassen (F1).
  - Keine **Flag-Argumente** (F3) und keine **Selektor-Argumente** (G15). Die Funktion wird in mehrere aufgeteilt.
  - Keine **Output-Argumente** (F2). Zustand des eigenen Objekts ändern oder einen Wert zurückgeben.
- **Keine Seiteneffekte.** Keine versteckten Zustandsänderungen und keine zeitlichen Kopplungen (G31). Eine nötige Reihenfolge macht man explizit, indem eine Funktion das Ergebnis der vorherigen übergibt.
- **Command-Query-Separation:** Eine Funktion tut entweder etwas oder beantwortet etwas, nie beides.
- **Exceptions statt Fehlercodes.** `try/catch`-Rümpfe in eigene Funktionen auslagern. Fehlerbehandlung ist „eine Sache“, also steht in einer Funktion mit `try` nichts vor dem `try` und nichts nach `catch`/`finally`.
- **DRY.** Duplikation ist die Wurzel allen Übels in Software.
- Strukturierte Programmierung: In kleinen Funktionen sind mehrere `return`/`break`/`continue` in Ordnung, `goto` nie.
- Vorgehen: erst funktionierend und unordentlich schreiben, dann mit grünen Tests verfeinern. Niemand schreibt clean im ersten Wurf.

## 3. Kommentare (Kap. 4)

> „Don't comment bad code – rewrite it.“ Kommentare kompensieren das Versagen, sich im Code auszudrücken.

- **Erlaubt:** juristische Header, informative Kommentare (z. B. Regex-Format), **Absicht/Warum**, Klarstellung bei fremden APIs, **Warnung vor Konsequenzen**, `TODO`, Verstärkung (warum etwas Unscheinbares wichtig ist), Doku-Kommentare für **öffentliche** APIs.
- **Verboten:** Gemurmel, redundante Kommentare (C3), irreführende Kommentare, Pflichtkommentare je Funktion, Journal/Changelog (C1), Rauschen (`/** Default constructor */`), Positionsmarker (`// ////// Actions`), Kommentare an schließenden Klammern, Autoren-Zuschreibungen, **auskommentierter Code** (C5, sofort löschen), HTML in Kommentaren, nicht-lokale Information, zu viel Information, Kommentare mit unklarem Bezug, Funktions-Header bei kleinen Funktionen, Doku-Kommentare in nicht-öffentlichem Code.
- Veraltete Kommentare (C2) werden aktualisiert oder gelöscht. Schlecht geschriebene (C4) werden sorgfältig neu formuliert.

## 4. Formatierung (Kap. 5)

- **Zeitungsmetapher:** oben Name und Überblick, nach unten zunehmend Details.
- **Vertikale Offenheit:** Leerzeile zwischen Konzepten. **Vertikale Dichte:** Zusammengehöriges steht eng beieinander.
- **Vertikaler Abstand** (G10): Variablen nah an ihrer Verwendung, Instanzvariablen oben in der Klasse. Abhängige Funktionen stehen untereinander, der Aufrufer über dem Aufgerufenen. Konzeptuell Verwandtes steht nah beieinander.
- Kurze Zeilen (≈ 100–120 Zeichen). Leerzeichen zeigen Zugehörigkeit (`a*b + c*d`). **Keine horizontale Ausrichtung** von Deklarationen. Einrückung nie aufgeben, auch nicht bei Einzeilern.
- **Teamregeln schlagen persönlichen Stil** (G11, G24). Konventionen des umgebenden Codes übernehmen.

## 5. Objekte und Datenstrukturen (Kap. 6)

- **Datenabstraktion:** Objekte verbergen Daten hinter Verhalten, keine blinden Getter/Setter für jedes Feld.
- **Objekt/Daten-Antisymmetrie:** Objekte machen neue Typen leicht und neue Funktionen schwer. Datenstrukturen sind umgekehrt. Bewusst wählen.
- **Keine Hybride** aus halb Objekt und halb Datenstruktur.
- **Gesetz von Demeter** (G36): Eine Methode ruft nur Methoden der eigenen Klasse, selbst erzeugter Objekte, ihrer Argumente und ihrer Instanzvariablen auf. **Keine Zugwracks** wie `a.getB().getC().doIt()`. Stattdessen sagt man dem Objekt, was es tun soll.
- DTOs bzw. Records für reine Daten ohne Verhalten.

## 6. Fehlerbehandlung (Kap. 7)

- Exceptions statt Rückgabecodes. Den `try-catch-finally`-Block zuerst schreiben, er definiert eine Transaktion.
- Unchecked Exceptions bevorzugen. Checked Exceptions verletzen das Open-Closed-Prinzip.
- **Kontext mitgeben:** Operation und Fehlerart in die Meldung.
- Exception-Klassen nach den Bedürfnissen des **Aufrufers** definieren. Fremd-APIs wrappen und auf einen eigenen Typ abbilden.
- **Special-Case-Pattern** statt Sonderfall-Behandlung beim Aufrufer (G33).
- **Kein `null` zurückgeben, kein `null` übergeben.** Stattdessen leere Collections, Special-Case-Objekte oder Exceptions.
- Fehler nie verschlucken. Kein `catch`, das nur loggt.

## 7. Grenzen (Kap. 8)

- Third-Party-Code an der Grenze kapseln. Keine `Map`- oder Bibliothekstypen quer durch die öffentliche API reichen.
- **Learning Tests:** Verhalten fremder APIs mit Tests festhalten, bevor man darauf baut.
- Noch nicht existierende APIs hinter einer eigenen Wunsch-Schnittstelle plus Adapter verbergen.

## 8. Unit Tests (Kap. 9)

- **Drei Gesetze des TDD:** (1) Kein Produktionscode ohne einen fehlschlagenden Test. (2) Nicht mehr Test schreiben, als zum Fehlschlagen nötig ist. (3) Nicht mehr Produktionscode schreiben, als den Test grün macht.
- Testcode ist genauso sauber wie Produktionscode. **Lesbarkeit** zählt am meisten. Build-Operate-Check bzw. Given-When-Then, gern mit eigener domänenspezifischer Testsprache.
- **Ein Konzept pro Test.** Wenige Asserts.
- **F.I.R.S.T.:** Fast, Independent, Repeatable, Self-Validating, Timely.
- Grenzen testen (T5), um Bugs herum gründlich testen (T6), triviale Tests nicht weglassen (T3). Tests müssen schnell sein (T9).

## 9. Klassen (Kap. 10)

- **Reihenfolge:** öffentliche Konstanten → private statische Variablen → private Instanzvariablen → öffentliche Methoden. Private Helfer stehen direkt nach ihrem Aufrufer.
- **Klein**, gemessen in **Verantwortlichkeiten**. Der Klassenname beschreibt sie ohne „und“, „oder“, „aber“. Namen wie `Processor`, `Manager` oder `Super` deuten auf zu viele Aufgaben hin.
- **Single Responsibility Principle:** genau ein Grund zur Änderung.
- **Hohe Kohäsion:** Wenige Instanzvariablen, und die Methoden nutzen möglichst viele davon. Sinkt die Kohäsion, wird die Klasse geteilt.
- **Open-Closed:** Erweitern durch neue Klassen statt Ändern bestehender.
- **Dependency Inversion:** von Abstraktionen abhängen, nicht von konkreten Details.
- Basisklassen kennen ihre Ableitungen nicht (G7). Keine Vererbung nur wegen Konstanten (G13, J2).

## 10. Systeme (Kap. 11)

- **Konstruktion von Nutzung trennen:** `main` bzw. Factories oder Dependency Injection bauen das Objektnetz, die Anwendung benutzt es nur.
- Querschnittsbelange (Persistenz, Transaktionen, Security) nicht in die Fachlogik streuen.
- Entscheidungen bis zum letzten vertretbaren Moment aufschieben. Standards nur nutzen, wenn sie nachweisbar Wert bringen.
- Konfigurierbare Daten auf hoher Ebene halten (G35). Keine Überkonfigurierbarkeit.

## 11. Nebenläufigkeit (Kap. 13)

- Nebenläufigkeitscode getrennt von anderem Code halten (SRP).
- Scope geteilter Daten minimieren. Kopien statt geteiltem Zustand. Threads möglichst unabhängig.
- Die Bibliothek kennen (thread-sichere Collections, Executors). Synchronisierte Abschnitte klein halten.
- Shutdown früh durchdenken. Nebenläufigen Code mit vielen Konfigurationen testen, sporadische Fehler nie als Einzelfall abtun.

## 12. Allgemeine Pflichtregeln

- **Pfadfinderregel:** Den Code sauberer hinterlassen, als man ihn vorgefunden hat. Das gilt für den angefassten Bereich. Ungefragte Großumbauten anderer Bereiche macht man nicht, sondern benennt sie.
- Offensichtliches Verhalten implementieren (G2). Grenzfälle korrekt behandeln (G3). Sicherheitsmechanismen nie abschalten, also keine Compiler-Warnungen ignorieren und keine Tests deaktivieren (G4).
- Präzise sein (G26). Struktur vor Konvention (G27). Nicht willkürlich sein (G32). Den Algorithmus verstehen, bevor man ihn baut (G21). Logische Abhängigkeiten physisch machen (G22).
- Bedingungen kapseln: `if (shouldBeDeleted(timer))` statt einer Langform (G28). Positiv formulieren statt `!` (G29). Erklärende Variablen nutzen (G19). Funktionsnamen sagen, was die Funktion tut (G20).
- Feature Envy (G14) vermeiden. Methoden dorthin legen, wo man sie erwartet (G17). Statisch nur, wenn kein Polymorphismus nötig ist (G18).
- Ursachen finden, nicht Symptome flicken.

## 13. Arbeitsablauf

1. **Vorher:** Gibt es das schon (DRY auch projektweit)? Den kleinsten Umfang wählen, der die Aufgabe löst.
2. **Schreiben:** Test zuerst (TDD), wo das Projekt Tests hat. Dann die Regeln oben anwenden.
3. **Refaktorieren** bei grünen Tests, Schritt für Schritt, Verhalten strikt erhalten.
4. **Abschluss-Check** am eigenen Diff:
   - [ ] Tests, Typecheck und Linter sind grün (Regel 1).
   - [ ] Keine Duplikation (G5).
   - [ ] Namen offenbaren die Absicht und sind konsistent (N1–N7, G11).
   - [ ] Funktionen sind klein, tun eine Sache auf einer Ebene, haben ≤ 3 Argumente, keine Flags und keine Output-Argumente (F1–F3, G30, G34).
   - [ ] Keine Seiteneffekte. Command-Query-Separation ist eingehalten.
   - [ ] Kein `null` zurückgegeben oder übergeben. Exceptions tragen Kontext. Nichts wird verschluckt.
   - [ ] Keine Zugwracks (G36). Keine magischen Zahlen (G25).
   - [ ] Kein toter, auskommentierter oder überflüssiger Code bzw. Kommentar (F4, G9, G12, C1–C5).
   - [ ] Jedes Element hat einen Zweck, nichts Überflüssiges (Regel 4).
5. Bei `/clean-code <pfad>`: Datei oder Ordner nach diesem Skill refaktorieren und die gefundenen Heuristik-Codes nennen. Danach Tests und Typecheck ausführen und Netto-LOC-Differenz berichten.
