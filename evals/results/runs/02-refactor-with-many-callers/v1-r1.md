```ts
const BOOK_MEMBER_FACTOR = 0.9;
const DEFAULT_MEMBER_FACTOR = 0.95;
const SAVE10_COUPON = "SAVE10";
const SAVE10_DISCOUNT = 10;

export function getPrice(p: any, isMember: boolean, coupon?: string) {
  const priceAfterMembership = isMember
    ? p.price * memberFactorFor(p.category)
    : p.price;
  const priceAfterCoupon = applyCoupon(priceAfterMembership, coupon);
  return roundToCents(priceAfterCoupon);
}

function memberFactorFor(category: string) {
  return category === "books" ? BOOK_MEMBER_FACTOR : DEFAULT_MEMBER_FACTOR;
}

function applyCoupon(price: number, coupon?: string) {
  return coupon === SAVE10_COUPON
    ? Math.max(0, price - SAVE10_DISCOUNT)
    : price;
}

function roundToCents(price: number) {
  return Math.round(price * 100) / 100;
}
```

**What changed**
- The nested `if`/`else` blocks and the mutated `price` variable are gone. `getPrice` now reads top-down as three steps: membership, coupon, rounding (G30, G34).
- Magic numbers and strings (`0.9`, `0.95`, `"SAVE10"`, `10`) are now named constants (G25).
- The membership and coupon rules each live in a small, named function (G28).
- The `if (coupon)` check was redundant, since `coupon === "SAVE10"` already fails for `undefined` and `""`. The `if (price < 0) price = 0` became `Math.max(0, …)`, which gives the same result, including for `NaN`.
- The order of operations is unchanged: member factor, then coupon, then rounding. Results are identical.

**Left alone on purpose**
- **Signature:** `getPrice(p: any, isMember: boolean, coupon?: string)` is unchanged because about 40 callers depend on it. Two smells remain that I can't safely fix without seeing those callers:
  - `p: any` should become a typed `{ price: number; category?: string }`.
  - `isMember` is a flag argument (F3). A cleaner design would be something like `getMemberPrice` and `getRegularPrice`, or passing a customer object.
- **Comparison operator:** `==` became `===`. For primitive strings this is identical. It would differ only if `category` were a `String` object, which is very unlikely.
- **Tests:** I couldn't run tests or the typecheck here. Please run your existing pricing tests. If there are none, a few characterization tests for the cases below would be worth adding before any further refactoring:
  - book vs. non-book
  - member vs. non-member
  - `SAVE10` on a price below 10
  - rounding
