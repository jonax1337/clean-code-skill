```ts
const BOOK_MEMBER_FACTOR = 0.9;
const DEFAULT_MEMBER_FACTOR = 0.95;
const SAVE10_COUPON = "SAVE10";
const SAVE10_AMOUNT = 10;

interface Product {
  price: number;
  category?: string;
}

export function getPrice(product: Product, isMember: boolean, coupon?: string): number {
  const memberPrice = isMember ? applyMemberDiscount(product) : product.price;
  const finalPrice = applyCoupon(memberPrice, coupon);
  return roundToCents(finalPrice);
}

function applyMemberDiscount(product: Product): number {
  const factor = product.category === "books" ? BOOK_MEMBER_FACTOR : DEFAULT_MEMBER_FACTOR;
  return product.price * factor;
}

function applyCoupon(price: number, coupon?: string): number {
  if (coupon === SAVE10_COUPON) {
    return Math.max(price - SAVE10_AMOUNT, 0);
  }
  return price;
}

function roundToCents(amount: number): number {
  return Math.round(amount * 100) / 100;
}
```

**What changed (heuristics addressed)**
- **Nesting and branching:** The nested `if`/`else` is now a single ternary for the factor (G28, G29), and the clamp is `Math.max(…, 0)`.
- **Magic numbers (G25):** `0.9`, `0.95`, `"SAVE10"` and `10` are named constants.
- **One abstraction level per function (G6, G30, G34):** `getPrice` reads as three steps (member discount, coupon, rounding), and each helper does one thing.
- **Mutation:** The reassigned `let price` is gone; everything is `const` and returns values.
- **Types:** `any` is replaced by a minimal `Product` interface, and `==` by `===`.

**Behavior preserved**
- Non-members keep `product.price` unchanged.
- Books get ×0.9 and everything else ×0.95 for members.
- `SAVE10` subtracts 10 and clamps at 0, and any other or empty coupon is ignored.
- The result is rounded to cents the same way.
- Even `NaN` behaves the same (`Math.max(NaN, 0)` is `NaN`, as before).

**Deliberately not changed**
- **Signature and export:** `getPrice(p, isMember, coupon?)` keeps its name and positional parameters because of the ~40 call sites. `isMember` is a flag argument (F3), and a later cleanup could replace it with a customer or pricing-context parameter. That would be a separate, mechanical migration.

**One thing to check**
- Replacing `any` with `Product` could surface type errors at call sites that pass objects without a numeric `price`. Those would be real bugs, but run the typecheck before merging. I couldn't run it here, so the change is unverified against your callers. If it's too noisy, temporarily keep `product: any` and tighten it in a follow-up.

I'd also add a few tests around this before merging (I haven't seen your test setup): member vs. non-member, books vs. other, `SAVE10` with a price under 10 (clamps to 0), an unknown coupon, and rounding.
