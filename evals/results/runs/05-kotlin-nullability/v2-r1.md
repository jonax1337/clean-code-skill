```kotlin
class UserService(private val repo: UserRepository) {

    fun displayName(id: Long): String? {
        val user = repo.findById(id) ?: return null
        return user.nickname?.takeIf { it.isNotBlank() }
            ?: "${user.firstName} ${user.lastName}"
    }
}
```

**What changed and why**

- **Null handling is idiomatic Kotlin.** The `findById` result is handled with `?: return null` instead of an `if (user == null)` block. The nullable return for "not found" stays, since in null-safe Kotlin that is the idiomatic form (section 7), and the public signature is unchanged.
- **Nickname check collapsed.** `user.nickname != null && user.nickname.isNotBlank()` becomes `nickname?.takeIf { it.isNotBlank() }`. Same behavior (null or blank falls through to the full name), with one fewer repeated access. It also doesn't depend on smart-casting `user.nickname`, which only works if the property is a stable `val` in the same module.
- **String concatenation replaced with a template** (`"${user.firstName} ${user.lastName}"`), the standard Kotlin form.

**Behavior preserved:** nickname if non-blank, otherwise "first last", otherwise `null` when the user doesn't exist.

**Left alone, deliberately**

- I didn't add an interface, extra helper, or comments. For three lines, the logic reads clearly as is.
- If `User` is yours to change, the fallback rule ("nickname, else full name") is a natural fit as a `displayName` property on `User` itself, which would remove the `user.x.y` reach-ins (G36, feature envy). That changes where the code lives and possibly callers, so I'm suggesting it rather than doing it.
