Here is the refactored handler:

```go
func (s *Server) handleGetUser(w http.ResponseWriter, r *http.Request) {
	id, err := parseUserID(r)
	if err != nil {
		http.Error(w, err.Error(), http.StatusBadRequest)
		return
	}

	user, err := s.db.FindUser(r.Context(), id)
	if err != nil {
		respondToFindUserError(w, id, err)
		return
	}

	respondWithJSON(w, http.StatusOK, user)
}

func parseUserID(r *http.Request) (int, error) {
	raw := r.URL.Query().Get("id")
	id, err := strconv.Atoi(raw)
	if err != nil {
		return 0, fmt.Errorf("invalid user id %q: %w", raw, err)
	}
	return id, nil
}

func respondToFindUserError(w http.ResponseWriter, id int, err error) {
	if errors.Is(err, store.ErrNotFound) {
		http.Error(w, "user not found", http.StatusNotFound)
		return
	}
	log.Printf("find user %d: %v", id, err)
	http.Error(w, "internal server error", http.StatusInternalServerError)
}

func respondWithJSON(w http.ResponseWriter, status int, body any) {
	w.Header().Set("Content-Type", "application/json")
	w.WriteHeader(status)
	if err := json.NewEncoder(w).Encode(body); err != nil {
		log.Printf("encode response: %v", err)
	}
}
```

**What changed and why**

- **Swallowed errors (the main fault):** `strconv.Atoi`'s error was discarded with `_`, so `?id=abc` silently looked up user 0. Now it returns a `400` with a message that includes the offending value.
- **Log-and-continue:** the old code logged the `FindUser` error and then encoded a nil/zero `user` as if it had succeeded. Each failure now ends the request with an explicit status and a `return`.
- **Caller-oriented mapping:** `store.ErrNotFound` is detected with `errors.Is` and becomes `404`. Any other error is logged with context (operation and id) and becomes a generic `500`, so internals don't leak to the client.
- **Encode error:** it is no longer ignored. Once the header has been written, the status can't change, so logging is the only remaining option there.
- **Structure:** the handler reads as a short story at one abstraction level. Parsing, error mapping and response writing each have their own small function with a single job.

Heuristics addressed: G4/G3 (ignored error and edge case), G30 and G34 (one thing per function, one abstraction level), G5 (JSON writing is reusable by other handlers), and the "don't just log" and "give context" error-handling rules.

I haven't compiled this or run any tests. Handler tests for `400`, `404`, `500` and `200` would be worth adding. The helpers are written as plain functions, so you can move them or make them methods to match the conventions in the rest of `Server`.
