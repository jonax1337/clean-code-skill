```java
private static final int PAYLOAD_MASK = 0x7F;
private static final int CONTINUATION_BIT = 0x80;
private static final int PAYLOAD_BITS_PER_BYTE = 7;

public static int readVarInt(ByteBuffer buf) {
    int value = 0;
    for (int shift = 0; shift < Integer.SIZE; shift += PAYLOAD_BITS_PER_BYTE) {
        byte current = buf.get();
        value |= (current & PAYLOAD_MASK) << shift;
        if (isLastByte(current)) {
            return value;
        }
    }
    throw new RuntimeException("VarInt too big: more than 5 bytes");
}

private static boolean isLastByte(byte current) {
    return (current & CONTINUATION_BIT) == 0;
}
```

**What changed**
- Magic numbers `0x7F`, `0x80`, `7` and `32` became named constants (G25). `32` is now `Integer.SIZE`.
- The `while (true)` with `break` and a manual `pos` counter became a bounded `for` loop. The exit condition is now visible in the loop header, and the early `return` replaces the `break` and the shared `return` (G29, structured control flow).
- `byte b` was declared outside the loop. It is now declared where it is used (G10), and renamed `current`.
- `pos` was a misleading name, since it holds a bit shift, so it is now `shift`.
- The continuation-bit check is encapsulated in `isLastByte` (G28).
- The exception message now says what the limit is.

**Behaviour is identical**
- Shifts go 0, 7, 14, 21, 28, so at most 5 bytes are read. The old code threw after the 5th byte if its continuation bit was still set, and the new code throws when the loop runs out. The same inputs produce the same results, including the dropped high bits on the 5th byte.
- The exception type is still `RuntimeException`, so existing callers are unaffected. A dedicated `VarIntTooBigException extends RuntimeException` would be the cleaner next step (Kap. 7), and it would remain compatible with callers that catch `RuntimeException`.

**Performance**
- The hot path is the same as before. It uses primitives only, with no allocation, no extra branches, and the same one `buf.get()` per byte.
- The constants are compile-time inlined. `isLastByte` is a tiny static method, which HotSpot inlines at this call site.
- I can't run a profiler here, so I haven't measured this. The code is not expected to be slower, but confirm with your benchmark or profiler.
- If this stays at ~12 %, the cost is more likely the per-byte `ByteBuffer.get()` bounds checks or the call frequency. Both are outside this method's structure, and I left them untouched.
