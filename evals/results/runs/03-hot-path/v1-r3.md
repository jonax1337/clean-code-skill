```java
private static final int PAYLOAD_BITS_PER_BYTE = 7;
private static final int PAYLOAD_MASK = 0x7F;
private static final int CONTINUATION_FLAG = 0x80;
private static final int INT_BITS = 32;

public static int readVarInt(ByteBuffer buf) {
    int value = 0;
    for (int shift = 0; shift < INT_BITS; shift += PAYLOAD_BITS_PER_BYTE) {
        byte current = buf.get();
        value |= (current & PAYLOAD_MASK) << shift;
        if (isLastByte(current)) {
            return value;
        }
    }
    throw new IllegalArgumentException("VarInt is longer than 5 bytes");
}

private static boolean isLastByte(byte current) {
    return (current & CONTINUATION_FLAG) == 0;
}
```

**What changed**
- **Magic numbers (G25):** `0x7F`, `0x80`, `7` and `32` are now named constants.
- **Loop structure:** `while (true)` with `break`, a manually incremented `pos` and a mid-loop check became a bounded `for`. The bound is visible in the loop header, and the exit paths are `return` on success and `throw` on overflow.
- **Condition (G28):** `isLastByte(current)` replaces the bit test, so the code reads as intent.
- **Names (N1):** `pos` is now `shift`, which is what the variable actually does. `b` is now `current`, declared inside the loop instead of at the top (G10).
- **Exception:** the message now says what is wrong. I used `IllegalArgumentException`, a subclass of `RuntimeException`, so existing `catch (RuntimeException)` code keeps working. If you want a dedicated protocol exception type, that's the better long-term choice.

**Behavior is identical**
- The shifts are 0, 7, 14, 21, 28, so at most 5 bytes are read.
- A continuation flag on the 5th byte still throws, just as the old `pos >= 32` check did.
- A truncated buffer still throws `BufferUnderflowException` from `buf.get()`.

**Performance**
- The loop does the same work per byte as before: one `get()`, one mask, one shift, one flag test. There are no allocations, no boxing and no extra branches.
- `isLastByte` is a tiny static method, so HotSpot should inline it. I haven't run the profiler or a benchmark here, so please confirm with a JMH benchmark or your profiler before merging.
- If 12 % is still too high, the bigger win is usually not in this function. Look at the per-field call pattern, for example a fast path for single-byte VarInts (`b >= 0` means no continuation bit) or reading from a `byte[]` instead of a `ByteBuffer`. I left those out because they change the structure and should be driven by measurements.
