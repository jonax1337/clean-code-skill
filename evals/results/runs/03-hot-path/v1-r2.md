```java
private static final int PAYLOAD_MASK = 0x7F;
private static final int CONTINUATION_FLAG = 0x80;
private static final int PAYLOAD_BITS_PER_BYTE = 7;
private static final int INT_BITS = 32;

public static int readVarInt(ByteBuffer buf) {
    int value = 0;
    for (int shift = 0; shift < INT_BITS; shift += PAYLOAD_BITS_PER_BYTE) {
        byte current = buf.get();
        value |= (current & PAYLOAD_MASK) << shift;
        if (isLastByte(current)) {
            return value;
        }
    }
    throw new IllegalArgumentException("VarInt is longer than 5 bytes");
}

private static boolean isLastByte(byte current) {
    return (current & CONTINUATION_FLAG) == 0;
}
```

**What changed**
- **Magic numbers (G25):** `0x7F`, `0x80`, `7` and `32` are now named constants, so the code says what it does.
- **Loop structure (G29, G30):** `while (true)` with `break`, a hand-managed `pos` and a mid-loop check became a bounded `for` loop. The limit is visible in the loop header, and the early `return` replaces the `break`.
- **Scope (G10):** `b` is declared inside the loop at its point of use, as `current`, instead of at the top of the function.
- **Condition (G28):** the bit test is wrapped in `isLastByte`.
- **Error (Ch. 7):** the exception now says what went wrong. I used `IllegalArgumentException` instead of a bare `RuntimeException`. It's a subclass, so existing `catch (RuntimeException)` callers still work. If you prefer a dedicated `VarIntTooBigException`, that's a one-line class.

**Behavior and performance**
- Behavior is identical. At most 5 bytes are read, and a continuation flag on the 5th byte throws. The old code reached the same result via `pos >= 32`. Overflow of the top bits in byte 5 is unchanged.
- It shouldn't be slower. There are no allocations, the same number of iterations and the same `buf.get()` calls. The constants are compile-time inlined, and `isLastByte` is a tiny static method that the JIT inlines. The exception path is cold. The loop-exit check is now in the loop header, but it compares the same values as before.
- I couldn't run tests or a benchmark here. Run your existing VarInt tests, especially the 5-byte max, the 6-byte overflow and the truncated-buffer cases. A quick JMH check against the old version would confirm the profile is unchanged.

**Not changed**
- If the 12 % is a real problem, the next lever is a fast path for the common one-byte case, or reading from a backing array instead of calling `buf.get()` per byte. That would add code and a second path, so I left it out as you didn't ask for it. I'd only do it with a benchmark showing it helps.
