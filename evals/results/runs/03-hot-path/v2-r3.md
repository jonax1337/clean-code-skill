```java
private static final int PAYLOAD_MASK = 0x7F;
private static final int CONTINUATION_BIT = 0x80;
private static final int PAYLOAD_BITS_PER_BYTE = 7;
private static final int MAX_BITS = Integer.SIZE;

public static int readVarInt(ByteBuffer buf) {
    int value = 0;
    for (int shift = 0; shift < MAX_BITS; shift += PAYLOAD_BITS_PER_BYTE) {
        byte current = buf.get();
        value |= (current & PAYLOAD_MASK) << shift;
        if ((current & CONTINUATION_BIT) == 0) {
            return value;
        }
    }
    throw new RuntimeException("VarInt too big: more than 5 bytes with continuation bit set");
}
```

**What changed**
- **G25 (magic numbers):** `0x7F`, `0x80`, `7` and `32` are now named constants.
- **G30/G34 (control flow):** `while (true)` plus `break` plus a manual `pos` counter is now a bounded `for` loop that returns as soon as the last byte is read. The `pos`/`b` declarations and the in-loop limit check are gone, and the exit conditions sit in one place.
- **Error message:** the exception now says what went wrong instead of just "VarInt too big".

**Behavior and performance**
- **Same behavior:** shifts go 0, 7, 14, 21, 28, so at most 5 bytes are consumed. If the fifth byte still has the continuation bit set, the method throws, as before. Overflow bits in the fifth byte are still dropped, as before.
- **Hot path:** there is no new allocation, no extra call, and no added branch. The constants are `static final` primitives, so javac inlines them. The loop is equivalent to the original and the JIT should treat it the same way, including unrolling a loop with at most 5 iterations. I haven't benchmarked this, so please confirm with your profiler.
- **Exception path:** the message is a constant string, so nothing extra is built unless the throw happens.

**Deliberately left alone**
- **Exception type:** `RuntimeException` is still thrown so existing catch sites behave identically. A dedicated exception such as `MalformedPacketException` would be better (a G-level readability gain, and it lets the proxy tell bad input from bugs), but that changes the API, so it's a separate decision.
- **No fast path for one-byte values:** the loop already returns on the first iteration for those, so a special case would add code without a measurable gain.
