```java
private static final int DATA_BITS_MASK = 0x7F;
private static final int CONTINUATION_BIT = 0x80;
private static final int DATA_BITS_PER_BYTE = 7;
private static final int INT_BITS = 32;

public static int readVarInt(ByteBuffer buf) {
    int value = 0;
    for (int shift = 0; shift < INT_BITS; shift += DATA_BITS_PER_BYTE) {
        byte current = buf.get();
        value |= (current & DATA_BITS_MASK) << shift;
        if ((current & CONTINUATION_BIT) == 0) {
            return value;
        }
    }
    throw new RuntimeException("VarInt too big");
}
```

**What changed**
- **Magic numbers (G25):** `0x7F`, `0x80`, `7` and `32` now have names. They are `static final` primitives, so javac inlines them and the bytecode is the same as with literals.
- **Loop shape (G29/G30):** the `while (true)` with `break`, a manually advanced `pos`, and a check in the middle is now a bounded `for`. The limit is visible in the loop header, and the happy path returns directly.
- **Names and scope:** `pos` is now `shift`, because it is a bit shift and not a buffer position (which is confusing next to `ByteBuffer`). `b` is declared inside the loop, where it is used.

**Behavior and performance**
- Behavior is identical. Shifts run 0, 7, 14, 21, 28, so at most 5 bytes are read. If the fifth byte still has the continuation bit, the method throws after consuming 5 bytes, same as before. Excess high bits in the fifth byte are still silently dropped by the shift.
- I kept the per-byte `buf.get()` loop with no extra allocations, branches or abstractions, so I expect no slowdown. I can't run anything here, so I haven't benchmarked it. Please re-check the profiler or a JMH run before merging.

**Deliberately left alone**
- I kept `RuntimeException("VarInt too big"). A dedicated exception type (for example a `MalformedPacketException`) would be cleaner, since the proxy probably wants to drop the connection on bad input. Changing it affects callers and any tests that assert on the type or message, so that should be a separate change.
- If the 12 % is still a problem, the next step is a fast path that reads from the backing array, or checks `buf.remaining()` once, instead of doing a bounds-checked `get()` per byte. That has a real cost in readability, so I'd only do it with a benchmark showing the gain.
