```java
private static final int VARINT_PAYLOAD_MASK = 0x7F;
private static final int VARINT_CONTINUATION_BIT = 0x80;
private static final int VARINT_BITS_PER_BYTE = 7;

public static int readVarInt(ByteBuffer buf) {
    int value = 0;
    for (int shift = 0; shift < Integer.SIZE; shift += VARINT_BITS_PER_BYTE) {
        byte current = buf.get();
        value |= (current & VARINT_PAYLOAD_MASK) << shift;
        if ((current & VARINT_CONTINUATION_BIT) == 0) {
            return value;
        }
    }
    throw new RuntimeException("VarInt too big: more than 5 bytes");
}
```

**What changed (G25, G30, N1, G29):**
- The magic numbers `0x7F`, `0x80` and `7` now have names (G25).
- `while (true)` with `break` and a manual `pos` counter became a bounded `for` loop. The exit condition is visible in the loop header, and the early `return` replaces the `break` plus trailing `return`. The `pos >= 32` check inside the loop is gone because the loop bound enforces it.
- `pos` is now `shift`, which says what it is. `b` is now `current`, and the `byte b` declaration moved into the loop, next to its use.

**Behavior is preserved:**
- The original read at shifts 0, 7, 14, 21 and 28, then threw if the 5th byte still had the continuation bit set (`pos` reached 35). The new loop runs the same five iterations and falls through to the throw in exactly that case.
- Overflow bits in the 5th byte are still silently truncated, as before.
- The exception type is still `RuntimeException`, so no caller's `catch` is affected. The message now says what the limit is. If you can touch callers, a dedicated exception type would let them tell a malformed packet from other failures.

**Performance (G-rule bent for a hot path):** I kept the loop structure and added no allocations, extra calls or abstractions. The constants are `static final` ints, so they are inlined at compile time. The loop does the same work per byte as before, so I expect the same JIT output or very close to it.
